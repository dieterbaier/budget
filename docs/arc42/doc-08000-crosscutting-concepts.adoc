= Crosscutting Concepts

== Domain Model

The domain is modelled with DDD tactical patterns (ADR-009). What each concept
below *means* is in xref:glossary[the glossary], which is the term register
(ADR-022); this section shows only how they hang together.

A frame is one aggregate. The four unframed classes are aggregates too — of a
single entity each — so they carry no label; only an aggregate with an interior
needs its root pointed out.

Identity: `Account` by IBAN/name, `CategoryGroup` and `Category` by name,
`Einkuenfte` by month. A `Transaction` needs identity and has no guaranteed
natural key, so it uses a bank reference or a generated `TransactionId`
(Q-ARCH-003).

`Money`, `Zahlungsintervall`, `Zahlungsmethode` and the typed identifiers are value
objects: no identity, compared by value. A `Kontostand` and a
`Vermoegensposition` value are entered by hand and never derived from a
`Transaction` (ADR-008). Persistence surrogate keys stay inside the JPA entities
and never appear in the domain (ADR-009).

== Rentenprognose And Vermoegen

The `Rentenprognose` works in *nominal* terms. Inputs are the current pension
pot, retirement age, life expectancy, an estimated nominal return the owner
enters (the rate a safe investment would yield today), and an inflation rate. The
inflation rate is the average of the `InflationSeries`, Germany's historical
annual rates, taken from
https://www.global-rates.com/de/inflation/historisch/[global-rates.com].

The expected monthly need in retirement is derived from current costs, but only
those flagged `rentenrelevant`: a `Category`, a `Transaction` and a
`Fixkostenposition` each carry the flag, so items such as a mortgage repayment
(assumed gone in retirement) are excluded. From the projected need over the
retirement span and the owner's `Vermoegen`, the domain computes the
`Rentenluecke`.

== Money Handling

All amounts are EUR and stored as exact decimals (`BigDecimal` / `numeric`); no
floating-point money. `Monatsanteil` and `Sollansparung` arithmetic rounds
explicitly.

== Security

Single-user authentication: one credential, Argon2 password hashing, sessions
over TLS only, server-side authorization on every endpoint, and no third-party
telemetry. Logs never contain `Transaction` descriptions or amounts tied to
identifiers.

== Testing

Features are Gherkin scenarios run by Cucumber-JVM against the application
boundary; the domain is unit-tested with JUnit 5, AssertJ, and Mockito; the
persistence adapter is tested against real PostgreSQL via Testcontainers. Money
rules are developed test-first.

== Observability

Backend logs carry request IDs, validation failures, and calculation errors,
with personal financial detail redacted.

== Error Handling

Invalid input is rejected at the API boundary with clear messages; the PWA shows
them inline. There is no offline queue — the client requires the backend to be
reachable.
