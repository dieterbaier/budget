= Solution Strategy

The backend is the system of record: a Spring Boot service in a Clean/Hexagonal
layout whose framework-free domain owns every money rule (monthly expenditure and
overspending, fixed-cost amortization, account reserves, cash runway, pension
projection). A single React + TypeScript PWA renders those results over a
versioned HTTP JSON API and serves both desktop and phone. Data lives in
PostgreSQL behind a persistence port, so the store can move from a local instance
to a hosted one without touching the domain. Account balances are manually
entered snapshots, not a derived ledger.

Features are specified in Gherkin and built test-first: Cucumber-JVM exercises use
cases at the application boundary; JUnit 5, AssertJ, and Mockito cover the domain;
Testcontainers exercises the PostgreSQL adapter.

The first increment is a walking skeleton: bootstrap the master data, record a
transaction, and show the current monthly expenditure with the overspending
signal.

== Implementing Clean Architecture In The Backend

A few implementation decisions realize the Clean/Hexagonal intent, each recorded
with its rationale as an ADR:

* *DDD tactical design* — the domain is value objects and aggregates whose
  entities carry *domain* identity (a business key, or a generated typed id where
  none exists), never a persistence surrogate key. See
  xref:adr-009-domain-identity-and-ddd[ADR-009].
* *Explicit bean configuration* — the application and domain layers have no Spring
  annotations; they are wired by explicit `@Bean` methods, and only the adapters
  are component-scanned, so the core stays framework-free and plain-Java testable.
  See xref:adr-012-explicit-bean-configuration[ADR-012].
* *Flyway migrations* — the schema evolves through versioned, plain-SQL scripts,
  with Hibernate in `validate` mode. See xref:adr-010-flyway-migrations[ADR-010].
* *No Lombok* — plain Java (records plus explicit code) instead of an annotation
  processor. See xref:adr-011-no-lombok[ADR-011].

Those four are documentation, and documentation decays quietly. ArchUnit rules
run with the backend test suite and fail the build when one of them is broken,
each rule naming the decision it protects. The rule groups are recorded as
constraints in xref:architecture-constraints[]; the choice of tool and of when
they run is xref:adr-013-architecture-fitness-functions[ADR-013].

== Structuring The Web Client

The client applies the same intent as the backend — a structure that names the
domain, with boundaries that are explicit rather than remembered — through means
that suit a React application.

`application/web/src` is organized *feature-first*: a directory per budget
concept, each privately owning its API calls, query hooks, components and page,
so `src/features` lists transactions, categories, fixed costs and the budget
views rather than listing React file types. A feature is reached only through
its `index.ts`, which makes that barrel the client's equivalent of a port: the
public surface is deliberate, and the interior is free to change. `src/app`
composes the features into the running application and `src/shared` holds only
what is genuinely cross-cutting, with `shared/ui` restricted to presentational
components that fetch nothing.

Two candidate styles were rejected and the reasons recorded, because both are
common enough to be proposed again: a `pages`/`components`/`api`/`queries` split,
which describes React rather than the budget and leaves "general or specific?"
open for every addition; and Atomic Design, whose atoms/molecules/organisms
taxonomy is not checkable and answers a different question than where a feature's
data access belongs. The one idea worth keeping from it — presentational
components separated from connected ones — survives as a dependency rule.
See xref:adr-014-frontend-architecture-style-and-stack[ADR-014].

Libraries are adopted against a named trigger rather than by habit. TanStack
Query replaces a hand-written refetch token and per-component request state;
UnoCSS retires a single global stylesheet that every feature would otherwise
have to edit. React Router waits for the second route, and axios waits for the
authentication work that would give an interceptor something to do — a decision
recorded now, taken later.

Responses are validated where they arrive. Zod schemas sit in each feature's
`api/` module and the client's HTTP helper parses with them instead of casting,
so a backend change that alters a shape fails at the seam with the field named
rather than surfacing as a rendering artefact; the TypeScript types are inferred
from those schemas, so a response has one definition. Describing the datatypes
once for both sides — generating a contract from the backend domain — was
explored and set aside: a generated contract coordinates units with independent
release cycles, and the client is built from the same commit as the server and
ships with it. See xref:adr-016-frontend-response-validation[ADR-016], which
records what that would have cost and the structural conditions that would make
it right.

This structure is checked the way the backend's is. ESLint with
`eslint-plugin-boundaries` fails the build on a deep import into another
feature's interior, on a cycle between features, and on shared UI reaching for a
feature or an API module. The rule group is
xref:con-005-feature-boundaries[CON-005]; the choice of tool is
xref:adr-015-frontend-architecture-fitness-functions[ADR-015].
