[[con-002-hexagonal-boundaries]]
== CON-002: Hexagonal Boundaries

The domain knows nothing outside itself, the application layer knows only the
domain, and infrastructure sits behind ports.

[cols="2,3", options="header"]
|===
| Rule | Enforces
| Dependencies point inwards | xref:adr-004-backend-stack-and-architecture[ADR-004]
| Outbound ports are interfaces | xref:adr-004-backend-stack-and-architecture[ADR-004]
| Adapters use ports, not use-case implementations | xref:adr-012-explicit-bean-configuration[ADR-012]
| HTTP controllers live in the inbound web adapter | xref:adr-001-backend-api-boundary[ADR-001]
|===

`BudgetApplication` sits in the root package and belongs to no layer. The layer
rule considers only dependencies between the declared layers, so the boot class
is ignored rather than forcing a layer to be invented for it.

The adapter ring is declared as reachable from the development layer only, not as
unreachable outright. The stricter form is the better intent and was tried: it
fails with 28 violations, every one of them `LocalDataSeeder` reaching the JPA
repositories. Passing it would mean deleting the seeder or adding save methods to
`CategoryRepository`, `FixedCostRepository` and `IncomeRepository` — widening
three production ports to serve a local-profile convenience. Naming the
development layer is the narrower price: no layer inside the hexagon may name an
adapter, and the seeder alone may. See
xref:con-003-persistence-isolation[CON-003] for the same exception seen from the
persistence side.

The rule that keeps adapters away from use-case implementations carries no
exceptions. `UnknownCategoryException` is what would have forced one:
`ApiExceptionHandler` maps it to a status code, which is a legitimate thing for
an inbound adapter to do, but the exception sat in `application.service` and so
looked like a dependency on the implementation package. It was moved to
`application.port.in`, where it belongs — a caller has to handle it, so it is
part of the use case's contract — and the rule stayed strict.
