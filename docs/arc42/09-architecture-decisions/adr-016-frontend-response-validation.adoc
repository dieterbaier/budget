[[adr-016-frontend-response-validation]]
== ADR-016: Frontend Response Validation With Zod

=== Status

Accepted. The choices were made by the owner in a design discussion on
2026-07-26; the owner reviewed and confirmed this record of them the same day.

=== Decision

The web client validates every API response against a Zod schema at its HTTP
seam. `shared/api` takes a schema and parses with it instead of casting, so a
payload that does not match fails where it arrives, reporting the offending
field together with the expected and received types.

A response that is not JSON at all fails the same way, naming the path, rather
than surfacing as a bare `SyntaxError` from `response.json()`. The seam is
therefore complete: a wrong status, an unparseable body, and a well-formed body
of the wrong shape all produce an error that says which request failed and why.

The response types are *inferred* from those schemas with `z.infer`, so a
response shape has one definition rather than a schema and a hand-written
`interface` that can disagree.

Schemas live in the owning feature's `api/` module, beside the call they
describe. They are internal to the feature unless another feature needs them,
like everything else behind a feature's barrel
(xref:con-005-feature-boundaries[CON-005]).

*Form* validation is deferred, not rejected. Native HTML validation covers the
current fields and brings accessible, localized browser messages for free. The
trigger is the first form with a rule the platform cannot express — a
cross-field rule such as the reserve depending on a payment interval, or the
runway depending on an account balance. This is the same named-trigger
discipline xref:adr-014-frontend-architecture-style-and-stack[ADR-014] applies
to React Router and axios.

A generated contract shared between backend and frontend is *not* adopted. The
reasoning is recorded below, because the idea is attractive enough to be
proposed again.

=== Context

`shared/api/http.ts` ended a read with `response.json() as Promise<T>`. That is
an assertion, not a check: nothing compared the payload to the type. A renamed
backend field would surface as `undefined`, then as `NaN` in a component, far
from its cause — and the compiler would report nothing, because the cast told it
not to. Alongside it, each response had a hand-written `interface` that no test
compared to a real payload.

The owner asked a broader question first: whether the backend domain could
describe the datatypes and their constraints once, for both sides. That is a
better idea than schema duplication and was explored in full before being set
aside; see the options.

=== Decision Drivers

* A wrong payload should fail at the boundary with a clear message, not deep
  inside a component as a rendering artefact.
* A response shape should have one definition, not two that can drift.
* Whatever is adopted must earn its place against *this* project — a single
  repository whose client and server are built from one commit and released
  together.
* Constraints that need server data cannot be checked on the client at all, so
  no design should imply that they can.

=== Considered Options

==== Zod schemas written in the client, validating responses (chosen)

One dependency, no code generation, no build step. Types are inferred, so the
duplication that mattered — schema versus interface — disappears rather than
being managed. The schema sits beside the call it describes, so a feature owns
its own contract with the backend.

`zod/mini` is used rather than the full build, with the English locale loaded
explicitly. Three variants were measured against a 47.1 KB gzipped baseline:

[cols="3,1,1", options="header"]
|===
| Variant | Gzipped | Increase
| `zod/mini`, no locale | 62.9 KB | +15.7 KB
| `zod/mini` + `en` locale | 63.9 KB | +16.7 KB
| Full `zod` | 77.6 KB | +30.4 KB
|===

The locale is what makes Mini viable. Without it Mini reports
`total: Invalid input`; with it, `total: Invalid input: expected number, received
string` — byte-identical to the full build's message, for about 1 KB. The full
build therefore costs 13.7 KB more than Mini for no difference in diagnostics at
all.

Note what Mini does *not* cost: the field path. Both variants name the offending
field. What the locale buys on top is the expected and received types, which is
the difference between knowing a field is wrong and knowing *how* — a renamed
field reports `received undefined`, a changed type reports `received string`. In
an application with no centralized error monitoring, that distinction is the
whole diagnostic.

Typing the shared helper against `zod/v4/core` is the mechanism Zod documents for
code that must accept schemas from either build; it is not a dependency on
private internals.

Its limitation is honest: the schema is written by hand from the backend's
actual response, so nothing *proves* it matches the server. What it does
guarantee is that a mismatch is caught immediately, at the seam, instead of
being rendered.

==== A contract generated from the backend domain

The owner's preferred shape, and explored in detail: annotate the domain, have
springdoc emit an OpenAPI document, and generate TypeScript and Zod from it. It
was rejected because none of its three viable forms survives contact with this
codebase.

Putting domain types in the DTOs makes `Money` — a record wrapping one
`BigDecimal` — serialize as `{"amount": …}`, so every amount in the JSON gains a
wrapper. Flattening it back with springdoc's `replaceWithClass` substitutes
`BigDecimal`'s schema and *discards* the constraint annotation that was the
entire point. Exposing domain types from the controllers instead needs
`@JsonValue` on `Money`, which is precisely the Jackson import
xref:con-001-framework-free-core[CON-001] predicts will arrive "smuggled in by a
serialization convenience on a domain type", and it makes any domain rename a
breaking change for an installed PWA. Annotating the domain while keeping the
DTOs primitive does work, but needs a bespoke per-field equivalence test and
leaves the duplication in place.

The deeper reason is structural rather than technical. A generated contract
earns its keep between units with *independent release cycles*; the PWA is built
from the same commit as the backend and ships with it, so the contract has no
independent lifetime to protect. The same test applies to API versioning and
gives the same answer there, which is what issue #31 records.

==== Keep the cast and rely on TypeScript

No dependency at all. It is what the code did, and the reason it is not enough
is that a cast is a promise to the compiler rather than a check of the data: the
one moment the type is worth verifying is the moment it crosses from a system
TypeScript cannot see.

=== Consequences

==== Positive

* A backend change that alters a response shape fails at the seam, naming the
  field and what it received, instead of rendering as `NaN` or `undefined`.
* A response that is not JSON — a proxy error page, a misrouted request — is
  reported against the path rather than as an unattributed `SyntaxError`.
* `z.infer` removes the hand-written response interfaces, so there is nothing to
  keep in step.
* The same schemas are available for form validation when a form needs more than
  the platform offers; adopting it later costs no new dependency.

==== Negative

* The schemas are written by hand against the backend's responses, so they can be
  wrong in the same way the interfaces could. The gain is *when* the error
  surfaces, not that it cannot happen.
* Validation runs on every response. On payloads this size the cost is not
  measurable, but it is not zero.
* The bundle grows by about 17 KB gzipped — 47.1 KB to 63.9 KB — to validate two
  response shapes. That is the cost of `zod/mini` with the English locale
  loaded; see the measurements below for why the full build was not used.
* A second definition of the response shape now exists — in the backend's DTO and
  in the client's schema. That is deliberate, and the option above records why
  removing it costs more than it saves here.
+
On the bundle: the service worker caches it, but that is supporting evidence
rather than the argument. Caching removes the repeated download; it does not
remove the first download, the download after each update, decompression,
parsing, or the storage on the device. The size is defensible here because 63.9
KB of JavaScript is small in absolute terms for a private single-user
application — not because caching makes it free. On a public, performance-
sensitive site the same 17 KB would deserve a harder look.

==== Neutral or Follow-Up

* The conditions that would reverse the contract decision are structural, not a
  matter of scale: a second client, an external consumer, separate repositories,
  or client and server released independently of one another. Domain size alone
  is not the trigger.
* Requests are not validated. The POST body is typed but not parsed, because the
  form deferral above covers it; revisit with the first cross-field form rule.
* `apiPost` still discards the response body. When a use case needs the created
  resource — issue #12 introduces transaction identity — that response gets a
  schema like any other.
