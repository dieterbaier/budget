== ADR-019: Resource Frugality As A Weighed Concern

=== Status

Proposed. The goal was set by the owner on 2026-07-26 and reframed by the owner
in review on 2026-07-27; this record is AI-drafted and is not accepted
architecture truth until the owner has reviewed the text.

=== Decision

Resource cost — bytes transferred, computation, storage, requests, infrastructure
capacity — is weighed openly when a decision is made, under three rules.

==== 1. Every resource claim declares its evidence level

Requiring a number for every claim sounds rigorous and is not. Before a
deployment exists, most honest knowledge is directional, and a rule demanding
measurement either suppresses that knowledge or dresses it up as something it is
not. So a claim states *what kind* of knowledge it is, and the measurement and
system boundary where one exists:

[cols="1,2,3", options="header"]
|===
| Level | Meaning | Example here
| *Measured* | Observed in the relevant build or running system | Zod Mini ships 13.7 kB gzipped less than the full build (xref:adr-016-frontend-response-validation[ADR-016])
| *Estimated* | Calculated from stated assumptions | Host energy from allocated power × runtime, once a host exists
| *Directional* | The direction is clear; the magnitude and environmental relevance are not | Disabling refetch-on-focus causes fewer requests
| *Hypothesis* | Plausible and worth investigating, not established | Always-on hosting may dominate this usage pattern
| *Unknown* | No responsible comparison can be made yet | Full-system carbon impact, before a deployment boundary exists
|===

A *directional* claim may decide a tie. It may not be presented as quantified
impact. The distinction is the whole point: it lets architecture work proceed
without measurement it cannot yet take, while keeping the record honest about
which is which.

==== 2. Frugality never compensates for a regression elsewhere

The conflict rule is in xref:quality-goals[the quality goals chapter] and is
normative: required quality scenarios are non-compensable minimums, options are
compared only among those that satisfy them, and QG-005 decides ties. Resource
savings cannot offset a correctness, privacy, security or usability failure.

==== 3. What can be measured is enforced, not reviewed

The web client's JavaScript carries two budgets
(xref:qs-003-web-client-payload[QS-003], checked by
xref:con-008-web-client-payload-budget[CON-008]). Everything else is a review
concern, and this ADR is explicit below about how much that leaves.

=== Context

Several decisions already served this concern before it was recorded, which is
the evidence that it is real rather than retrofitted. Each is labelled with the
level of evidence behind it:

[cols="2,2,1,1", options="header"]
|===
| Decision | Effect | Level | Where
| Zod Mini rather than the full build | −13.7 kB gzipped shipped | Measured | xref:adr-016-frontend-response-validation[ADR-016]
| Utility CSS generated on demand | CSS 4.20 → 3.08 kB | Measured | xref:adr-014-frontend-architecture-style-and-stack[ADR-014]
| No refetch on focus, no retries | fewer requests and less radio time | Directional | `app/queryClient.ts`
| Precached bundle | fetched once rather than per visit | Directional | xref:adr-005-web-client-as-pwa[ADR-005]
| Pipeline runs only what changed | a README typo starts no Testcontainers | Directional | xref:adr-020-selective-pipeline[ADR-020]
|===

None was made *for* this goal. Recording it is what makes the next one deliberate
rather than lucky.

=== Decision Drivers

* A goal nothing measures becomes a label applied after the fact to whatever was
  already decided.
* Sustainability claims are easy to make and hard to check, so the burden of
  proof must sit with the claim — without that burden becoming a reason to
  discard knowledge that is real but unquantified.
* An unbounded efficiency goal can be turned against correctness: fewer tests,
  less validation, weaker privacy. That would be a worse outcome than not having
  the goal.

=== Considered Options

==== Weighed with declared evidence, one enforced budget set (chosen)

Enforces what is measurable, labels what is not, and states how conflicts
resolve. It costs one build check, two numbers, and the discipline of saying
which kind of claim is being made.

==== Require a measurement for every claim

The first version of this ADR. It reads as more rigorous and is less honest: it
would have forced "always-on hosting probably dominates" either to disappear or
to masquerade as measurement. It also cannot be satisfied before deployment, so
in practice it would be ignored rather than met.

==== A broader set of enforced budgets

Request counts, build minutes, image sizes, a carbon estimate. More complete in
principle; in practice each needs a measurement this project cannot take
honestly, and a budget derived from a guess is worse than none because it looks
like evidence.

==== A goal without enforcement

Cheapest, and what most projects do. It is also the failure this repository keeps
writing decisions against: an assertion nothing can fail. QG-003 sat unenforced
until xref:adr-018-test-coverage-thresholds[ADR-018], and the day it was enforced
it found that `Money` had no test.

=== Consequences

==== Positive

* A resource claim is reviewable, because its evidence level is stated rather
  than implied.
* The budgets make the Zod Mini decision permanent — and that is now *verified*
  rather than asserted: reverting to the full build measures 74.0 kB gzipped,
  which the 70 kB ceiling rejects. The earlier 75 kB ceiling would have let it
  through, which is why the claim and the number were both wrong.
* Directional knowledge stays in the record instead of being discarded for
  lacking a number.

==== Negative

* *The enforced part is a client-side guardrail, not a statement about the
  system.* Bundle size is a proxy: it correlates with transfer, parse time and
  memory, but is none of them, and no threshold on it makes the application
  frugal.
* An evidence vocabulary can be gamed by labelling a guess *Estimated*. Nothing
  prevents that; the label only makes it visible enough to challenge.
* The conflict rule is more work at decision time than a ranking would be. That
  is deliberate — a ranking is what allows enough small savings to add up to a
  correctness defect on paper.

==== Neutral or Follow-Up

* *Hosting dominance is a hypothesis, not a conclusion.* For the expected usage
  pattern — one user, roughly one page load a day — always-on hosting is a
  plausible candidate for the dominant resource cost, but its contribution is
  unknown until issue #19 selects a deployment model. A shared host complicates
  allocating idle energy; an existing server may have very low marginal cost;
  scale-to-zero brings cold-start and embodied-cost trade-offs of its own. The
  bundle budgets are an independently useful client-side guardrail and are *not*
  evidence about which part of the system dominates.
* *The deployment decision therefore carries an obligation:* whatever #19 records
  must define its system boundary and functional unit, state its assumptions, and
  declare the evidence level of its comparison — the delivery chain spans server,
  network and end-user device, not transferred bytes alone. The Green Software
  Foundation's SCI for Web methodology is the reference for that framing.
* Backend resource cost is not budgeted at all, and nothing sensible can be
  measured until a deployment target exists.
