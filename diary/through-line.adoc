== The through-line

If these days have one theme, it is *green signals that check nothing*.

It came up ten times, in ten different disguises:

. a lint rule that reported no cycles because it could not parse the files it was following
. a locale setting that would have silently reverted to English
. an npm override that satisfied `npm audit` while breaking the library it pinned
. a shell check that printed success because it read the exit code of `tail`
. a payload budget calibrated so loosely that it did not reject the regression it was written for
. a test for a state bug that had never once seen the bug
. a claim that a shared query key made a refactor free, when it tripled the requests
. a fully tested monthly calculation that answered a different question than the product needed
. a container-engine probe reporting that podman was configured, on a host where podman could not start a container
. a PR check whose own comment promised the deployment would render, while that deployment was failing
. a grep for a term that reported the prose clean, in a file whose own list of occurrences said otherwise

Each one *passed*. None of them was checking anything.

The habit that came out of it, and which now applies to every guard added here:
**break it deliberately and watch it fail, or you do not know that it works.** A
guard that has never failed is a guard whose failure path has never been
executed.

It is worth being precise about why this keeps happening rather than treating it
as carelessness. A check has two ways to be quiet: because the thing it looks
for is absent, and because it is not looking. Both render identically. Nothing
in a passing build distinguishes them, and the reporting layer of most tools is
built to celebrate the first case without ever considering the second.

The ten above split along a second axis, which is the more useful one for
deciding where to spend suspicion:

Wrong wiring:: the cycle rule, the locale, the shell check, the container-engine
probe, the term grep. The tool was capable and was asked the wrong question, or
its answer was read wrong. These are found by feeding the tool a known-bad input.
+
The term grep is the cheapest specimen and the most embarrassing. It searched for
`anchorDate` in a repository where half the occurrences are prose and spelled
"anchor date". The known-bad input was sitting three lines above it, in the same
file, as a list of the places it should have found.
+
The engine probe is the clearest specimen of the whole family. `podman info`
answers "is podman configured?" and was read as "can podman run a container?".
Both are questions about podman; only one of them is the question that mattered,
and on the day it mattered they gave opposite answers.

Wrong threshold:: the payload budget. The tool worked perfectly and the number
was set where it could not bite. These are found by arithmetic against a real
regression, and never by running the check.

Wrong belief:: the npm override, the test that had never seen its bug, the
shared-query-key claim. The tool was fine and the mental model was not. These
are expensive, because everything downstream of the belief looks consistent —
and they are found only by measuring the thing believed.

Wrong question:: the monthly calculation. Nothing was miswired, no threshold was
slack, and no belief about the tooling was false. The tests verified that the
implementation matched the specification, correctly, and the *specification* was
wrong: we read a long-run average and the code computed the current
calendar month. This is the one the other three cannot reach. Testing harder does
not find it, because the tests were right about everything they were asked. It is
found only by putting the artifact next to the thing it is supposed to replace —
which here meant five screenshots of the tool we actually use.

The fourth category arrived last and is the most uncomfortable, because it has no
technical remedy. The first three are answered by better checking. This one is
answered by checking against *reality* instead of against the specification, and
nothing in a repository contains reality.

One of the ten is not a check at all: the PR-validation comment promising that a
green result meant the Pages deployment would render. A comment cannot fail, so
it cannot be broken deliberately, and the habit above has nothing to bite on. It
was written as a reassurance, it was believed, and it was wrong the first time
the machinery rather than the content broke.

Worth adding to the habit, then: **a claim in a comment is a check nobody can
run.** It gets the same scrutiny as an assertion or it does not get written.
