== Working agreements that emerged

None of these were agreed up front. Each one came out of something going wrong.

* *One issue, one branch, one PR, rebase merges only.*

* *One commit per slice of a request, with the "why" in the body.* These commit
  messages are the primary record and are written to be read later — the diff
  says what changed and only the message can say why it was worth changing.

* *AI-authored architecture content stays `proposed` / `reviewed: false` until
  the owner reviews it.* Marking one's own homework is not review.

* *Every dependency justifies itself against this project* — not against a
  reference stack, and not against another project it was borrowed from.

* *Every guard gets broken on purpose before it is trusted.* See the
  through-line; this is the rule the other six lessons collapse into.

* *Caveats need an ask.* Listing a concern that requires no action from the
  reader is noise. This was rightly called out, and the test is simple: if the
  reader cannot do anything with it, it is not a caveat, it is throat-clearing.

* *A claim in an issue or PR outlives the code it justified.* When a
  justification turns out to be wrong, the issue gets corrected too — not only
  the code.

=== On the collaboration itself

Two corrections from the owner shaped how the work is done more than any
technical decision did.

*Ask one question at a time.* A batch of three grilling questions is an
interrogation. The answers collide, and the least important question tends to
attract the most attention.

*Ceremony is a cost, not a virtue.* Filing an issue to describe a request that
was just made, or publishing a report that carries no signal a red pull request
does not, adds process without adding information. The stop test the owner
applies: without it, would a later reader probably decide wrongly or miss an
important assumption? If not, it does not get built.
