== Open threads

Things left deliberately unfinished, with the reasoning attached so the next
decision does not have to start from scratch.

The payload budget has 2.2 kB of headroom:: CON-008 sits at 98% of 92 kB. The
next dependency will hit the ceiling. The question at that moment is whether the
budget was set right or whether the payload genuinely grew — and it should be
raised deliberately with a named cause, in its own commit, the way the 70 kB →
92 kB raise for React Router was. Never nudged upward to make a build go green.

Quality reports are generated but not published:: budget issue #48 was closed as
not planned. Every gate already fails the build when broken, so a deployed
report adds no signal a red pull request does not, while costing build time and
storage on every merge. Recorded as a decision rather than an omission, because
"not published" reads like something forgotten.

Part of the toolkit follow-ups is still waiting on upstream:: the re-vendoring
half of budget issue #45 is done — `scripts/`, `templates/`, `metamodel/` and
`build.sh` are at toolkit `de7c2ad`, and `AGENTS.md` carries the pin, the resync
date and the exact divergence. What remains still waits on toolkit issue #68:
replacing ADR-001's hand-written admonition with the generated include, and
deleting the local `refine-adr` skill if upstream guidance then covers it. Until
then the hand-written note stays, marked as a stopgap.

The engine override is a workaround, not a diagnosis:: both workflows pin
`DOCS_TOOLBOX_ENGINE: docker` because podman on the GitHub runner intermittently
cannot start the container. Why it fails there is still unknown — the runner
image version was identical between a passing and a failing run, so the obvious
explanation (an image roll) is ruled out and no better one replaced it. Docker is
demonstrably healthy on those runners, so pinning it is a sound decision on the
evidence, but the evidence is thin. If it recurs on docker, or if podman starts
working again, the pin should be revisited rather than left as folklore. Toolkit
#71 records the faithful-probe alternative that was rejected on cost.

The proportionality gate is not yet applied here:: budget issue #42 waits for
toolkit issue #66 to define the test. Applying a home-made version first would
defeat the purpose of validating the toolkit's.

The evidence-level vocabulary is unproposed:: Measured / Estimated / Directional
/ Hypothesis / Unknown works well enough here to be worth offering upstream, but
one project is not evidence. It should survive longer first.

`Verwendungszweck` has no aggregate boundary:: ADR-009's aggregate map does not
cover it, and #58 specifies the concept — identity, its own lifecycle, belonging
to exactly one `Category` — without settling whether it is a root of its own, an
entity inside the `Category` aggregate, or a third cut. The chapter 8 diagram
draws it dashed rather than choosing, because a diagram that picks a boundary
decides it. The decision belongs in ADR-009 or a record refining it, and it has
to be made before #58 is implemented rather than discovered during it.

How a name-as-identity reaches the API is decided in two comments and no record:: ADR-009
makes the name the identity for `Category` and `CategoryGroup`, and it does the
same for `Account` (IBAN or name) and `Einkuenfte` (month). #82 settled how one
of those travels over HTTP — in the query string, because a path segment cannot
carry a slash — but settled it for two controllers, in their comments. #9 and #11
will each address a name-identified resource and will each meet the question
again, with nothing to inherit from. Whether that is worth an ADR is genuinely
open: it is one sentence of consequence, which is exactly the case toolkit issue
#66 says should not become a ceremonial record. The cheaper answer may be a line
in ADR-009 or in chapter 8, and the thing to avoid is discovering it a third time.

=== A process note, learned the hard way

Stacked pull requests need the dependent PR retargeted to `main` *before* the
one below it merges.

Merging the base PR deletes its branch, which auto-closes every PR pointing at
it — and a closed PR's base can be neither retargeted nor reopened. That cost
PR #52, which had to be recreated as #54 with identical content. PR #53 was
retargeted pre-emptively and survived the same deletion.

It cost the same thing again on 2 August. #75 was integrated with
`--delete-branch` while #78 still pointed at `issue_68`; #78 closed and had to be
recreated as #80. The note above was already in this file, written after the
first time, and nobody opened it. That is the more useful half of the second
occurrence: a rule that lives only in prose is re-learned at full price, and
this is the strongest local argument for #72 — the issue about which language
rules can be made checkable at all.
