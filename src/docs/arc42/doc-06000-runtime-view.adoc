= Runtime View

== Record A Transaction

The application layer never touches PostgreSQL directly. It depends on an
outbound *repository port*; the persistence adapter implements that port and is
the only component that speaks JPA/SQL. This keeps every infrastructure
interaction behind an adapter, as Clean/Hexagonal architecture requires.

[plantuml,transaction-entry-runtime,png]
----
@startuml
actor Owner
participant "Web PWA" as Web
participant "HTTP Adapter\n(inbound)" as Api
participant "Application\n(use case)" as App
participant "Budget Domain" as Domain
participant "Repository Port" as Port
participant "Persistence Adapter\n(outbound)" as Repo
database "PostgreSQL" as Db
Owner -> Web: Enter transaction (date, amount, category, account, type)
Web -> Api: POST /transactions
Api -> App: RecordTransaction use case
App -> Domain: Validate (expense / income / transfer, refund = negative)
App -> Port: save(transaction)
Port -> Repo: (implemented by)
Repo -> Db: INSERT
Db --> Repo: ok
Repo --> App: saved
App -> Port: load month data for summary
Port -> Repo: query
Repo -> Db: SELECT
Db --> Repo: rows
Repo --> App: transactions
App -> Domain: compute monthly summary
App --> Api: Updated monthly summary
Api --> Web: 201 Created + summary
@enduml
----

== Current Monthly Expenditure

On request, the application loads the month's data through the repository port and
asks the domain to sum the current month's variable costs, add each fixed cost
amortized to its monthly average (yearly ÷ 12, quarterly ÷ 3, and so on), exclude
transfers, apply refunds as negative amounts in their category, and compare the
total against the average monthly income to produce the overspending signal. The
same domain services feed the group view, the reserve requirement for the
non-monthly-fixed-cost account, and the pension projection. All figures are
computed on the backend (ADR-003); the PWA only renders them.
